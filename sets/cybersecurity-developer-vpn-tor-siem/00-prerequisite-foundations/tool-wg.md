# Tool Reference — wg

Deep-dive companion to `key-generation.md`, which uses only `wg genkey | tee wg-private.key | wg
pubkey > wg-public.key` (item 8 in that file). This file documents the full `wg` CLI — every
sub-command, flag, and configuration-file field, not just the two used there.

## Scope

The entire `wg(8)` man page is in scope — `wg` is a small, focused tool (nine sub-commands total),
so no exclusions are needed the way they are for `openssl` or `gpg` elsewhere in this batch.
Covered here: key generation (`genkey`, `pubkey`, `genpsk`), live interface inspection (`show`,
`showconf`), live interface configuration (`set`, `setconf`, `addconf`, `syncconf`), the
INI-based configuration file format those last four sub-commands share, environment variables, and
the debugging-information mechanism.

**Explicitly NOT covered**: `wg-quick(8)` is a *separate* shell-script tool (its own man page,
shipped in the same `wireguard-tools` package) that wraps `wg` plus `ip-link(8)`/`ip-address(8)`/
`ip-route(8)` to manage a WireGuard interface's full lifecycle — bringing it up/down, assigning
addresses, installing routes, and (optionally) rewriting DNS via `resolvconf`/`openresolv`. `wg`
itself only ever talks to an *already-existing* interface (created separately with
`ip link add ... type wireguard`) and never touches routing or DNS. Anywhere this file says
"interface," it means one `wg`/the kernel already knows about — `wg` cannot create one.

## Command syntax

```
wg [ COMMAND ] [ OPTIONS ]... [ ARGS ]...
```

If `COMMAND` is omitted, it defaults to `show` — bare `wg` is equivalent to `wg show`. Verified on
this machine: with no WireGuard interfaces present, both `wg` and `wg show` exit `0` and print
nothing (no error for "no interfaces" — an empty result is not a failure condition).

Sub-commands that take an `<interface>` argument require an interface that already exists at the
kernel/userspace-implementation level; `wg` cannot create one (see [Scope](#scope)).

## Key generation

### genkey

```
wg genkey
```

Generates a random Curve25519 private key and prints it, base64-encoded, to stdout. No flags, no
arguments — output goes straight to the pipe/terminal.

| Flag/arg | Meaning | Notes/gotchas |
|---|---|---|
| *(none)* | `genkey` takes no options or arguments | the entire sub-command is "generate one key, print it" |

**Concerning fact — why the output should never touch a temp file**: `wg genkey`'s only I/O is
stdout. The moment that output is written to *any* intermediate file (even briefly, even one that
gets deleted afterward), the private key material exists on disk with whatever permissions the
process's umask produced at that instant, and it may also survive in filesystem journal/snapshot
history, swap, or a crash dump. Piping directly (`wg genkey | wg pubkey`, or `wg genkey | tee
dest.key | wg pubkey > pub.key` when you *do* want to persist the private key) keeps the private
key in kernel pipe buffers rather than round-tripping through a shell variable, a `>` redirect to a
scratch file, or command substitution — none of which is safer than the direct pipe and some of
which are meaningfully worse (shell history, `/proc/<pid>/cmdline` exposure if passed as an
argument instead of via stdin/a pipe).

**Concerning fact — umask before the pipe, not chmod after**: the man page's own canonical example
for the combined generate step is:

```
$ umask 077
$ wg genkey | tee private.key | wg pubkey > public.key
```

Setting `umask 077` *before* `tee` creates `private.key` means the file is created with `0600`
permissions from the instant `tee` opens it — there is no window where the file briefly exists
world- or group-readable before a follow-up `chmod` fixes it. This is stronger than "create the
file, then `chmod 600` it" (the pattern `key-generation.md` uses for the `openssl`/`ssh-keygen`
entries), which has exactly that gap between creation and permission-tightening. Prefer `umask 077`
first when generating `wg` keys.

### pubkey

```
wg pubkey
```

Reads a private key (generated by `genkey`, base64-encoded) from stdin, and prints the
corresponding Curve25519 public key, base64-encoded, to stdout.

| Flag/arg | Meaning | Notes/gotchas |
|---|---|---|
| *(none)* | `pubkey` takes no options or arguments; input is always stdin | this is a **one-way derivation** — public from private, never the reverse. The output is safe to share/commit; the input must not be |

The man page gives the canonical combined-generation one-liner (with the `umask` step included):

```
$ umask 077
$ wg genkey | tee private.key | wg pubkey > public.key
```

`key-generation.md`'s command (`wg genkey | tee wg-private.key | wg pubkey > wg-public.key`) is
this same pattern, minus the `umask 077` step — see the gotcha above for why adding it is worth
doing.

### genpsk

```
wg genpsk
```

Generates a random pre-shared key (PSK), base64-encoded, and prints it to stdout. Unlike
`genkey`/`pubkey`, this is **not** a Curve25519 asymmetric keypair component — it is a symmetric
256-bit random value used purely to mix additional entropy into the handshake.

| Flag/arg | Meaning | Notes/gotchas |
|---|---|---|
| *(none)* | `genpsk` takes no options or arguments | output format matches `genkey`'s (32 raw bytes, base64-encoded) even though the cryptographic role is different |

**Why it exists**: WireGuard's handshake is Curve25519 Diffie-Hellman plus ChaCha20-Poly1305 —
strong today, but like all public-key cryptography it is a target for a hypothetical future
quantum adversary using Shor's algorithm. Mixing in a PSK (a value with no public-key structure at
all) means an attacker would need to break *both* the asymmetric handshake *and* recover the
out-of-band-distributed PSK to decrypt traffic — the man page calls this "post-quantum resistance"
for exactly that reason. The PSK is optional per-peer and must be distributed out-of-band (it has
no public counterpart to derive or publish).

### Key format: Curve25519 + base64

- **Raw key material**: both private and public WireGuard keys are 32 raw bytes — a Curve25519
  scalar (private) or the corresponding Montgomery-curve point (public).
- **Encoding**: `wg` always presents keys as base64, never raw/hex. Base64-encoding 32 bytes
  produces `ceil(32/3) * 4 = 44` characters, and because `32 mod 3 == 2`, the encoding always ends
  in exactly one `=` padding character.
- **Verified against the man page's own example** (`CONFIGURATION FILE FORMAT EXAMPLE` section):
  the sample private key `yAnz5TF+lXXJte14tji3zlMNq+hd2rYUIgJBgB3fBmk=` is 44 characters long
  (confirmed with `wc -c` on this machine), matching the 44-char/one-`=` pattern exactly.
- **Practical implication**: any string you're handed that claims to be a WireGuard key but is not
  44 base64 characters ending in `=` is not a valid key (or has been mangled — e.g. by an editor
  that trimmed trailing whitespace/the pad character, or line-wrapped it).
- Private keys generated by `genkey` and PSKs generated by `genpsk` are format-identical (44 base64
  chars) even though their cryptographic role differs — see [genpsk](#genpsk) above. Only context
  (which sub-command produced it / which config field it's assigned to) distinguishes them.

## Interface inspection

### show

```
wg show { <interface> | all | interfaces } [public-key | private-key | listen-port | fwmark |
peers | preshared-keys | endpoints | allowed-ips | latest-handshakes | persistent-keepalive |
transfer | dump]
```

| Argument | Meaning | Notes/gotchas |
|---|---|---|
| `<interface>` | show one named interface | default target if omitted is `all` |
| `all` | every WireGuard interface | this is the default when neither `<interface>` nor `interfaces` is given |
| `interfaces` | print a list of interface *names* only, one per line, then exit | does not print any configuration — just discovery |
| `public-key` | filter: interface's own public key | script-friendly single-value/line output |
| `private-key` | filter: interface's own private key | subject to `WG_HIDE_KEYS` when going to a TTY — see [Environment variables](#environment-variables) |
| `listen-port` | filter: UDP listen port | |
| `fwmark` | filter: outgoing fwmark | |
| `peers` | filter: list of peer public keys | |
| `preshared-keys` | filter: each peer's PSK (or `(none)`) | also subject to `WG_HIDE_KEYS` |
| `endpoints` | filter: each peer's current endpoint `ip:port` | reflects the *most recently observed* source of authenticated traffic, not necessarily the configured `Endpoint` — see `set`'s `endpoint` gotcha below |
| `allowed-ips` | filter: each peer's AllowedIPs list | |
| `latest-handshakes` | filter: Unix timestamp of each peer's most recent successful handshake | `0` means "never" |
| `persistent-keepalive` | filter: configured keepalive interval per peer | `off` if unset |
| `transfer` | filter: cumulative rx/tx byte counters per peer | |
| `dump` | machine-readable full dump, tab/newline-delimited | see exact field order below |

**Output modes**:
- No trailing filter argument → "visually pleasing" human-readable output meant for a terminal
  (colorized per `WG_COLOR_MODE`).
- A specific filter argument → script-friendly output: one line per interface (or peer), fields
  tab-separated. If `all` was used as the interface selector, the *first* field of every line is
  the interface name (so output from multiple interfaces can be told apart).
- `dump` → the densest script-friendly form. First line: `private-key`, `public-key`,
  `listen-port`, `fwmark` (tab-separated). One subsequent line per peer:
  `public-key`, `preshared-key`, `endpoint`, `allowed-ips`, `latest-handshake`, `transfer-rx`,
  `transfer-tx`, `persistent-keepalive` (tab-separated). This exact field order is worth
  memorizing if you're piping `wg show <if> dump` into `awk`/`cut` for monitoring scripts.

**Gotcha — `WG_HIDE_KEYS` affects only the pretty-printed (no-filter) mode.** Explicit filters like
`private-key` or `preshared-keys`, and `dump`, always print the real key material regardless of
that environment variable — the hiding is a display convenience for the human-facing view, not an
access control. Anyone who can run `wg show <if> dump` can read private keys whether or not
`WG_HIDE_KEYS` is set. (Reading the *private* key of an interface you don't own generally requires
root/appropriate netlink privileges in the first place — the env var doesn't add or remove that
requirement.)

### showconf

```
wg showconf <interface>
```

| Argument | Meaning | Notes/gotchas |
|---|---|---|
| `<interface>` | interface to dump | required, no default |

Prints the interface's current configuration in the same INI format `setconf` consumes (see
[Configuration file format](#configuration-file-format)) — i.e. this is the read-side counterpart
to `setconf`, and the two are meant to round-trip. Unlike `show <if> dump`, this includes field
names/section headers, not just tab-separated values, and it is meant to be redirected straight to
a `.conf` file: `wg showconf wg0 > wg0-saved.conf`.

## Live interface configuration

### set

```
wg set <interface> [listen-port <port>] [fwmark <fwmark>] [private-key <file-path>]
       [peer <base64-public-key> [remove] [preshared-key <file-path>] [endpoint <ip>:<port>]
        [persistent-keepalive <interval-seconds>]
        [allowed-ips [+|-]<ip1>/<cidr1>[,[+|-]<ip2>/<cidr2>]...]
       ]...
```

Applies configuration changes to a **running** interface without needing a config file — the
imperative counterpart to `setconf`. Multiple `peer` blocks may be given in one invocation.

| Flag/arg | Meaning | Notes/gotchas |
|---|---|---|
| `listen-port <port>` | UDP port to listen on | omitted or `0` → a random port is chosen when the interface next comes up |
| `fwmark <fwmark>` | 32-bit mark applied to outgoing packets | `0` or `"off"` disables it; hex accepted with a `0x` prefix |
| `private-key <file-path>` | path to a file containing the interface's base64 private key | **must be a file path, not the key on the command line** — args are visible to other local users via `/proc/<pid>/cmdline` on most systems. bash users may pass a string via process substitution: `private-key <(echo PRIVATEKEYSTRING)`. Passing `/dev/null` (or any other empty file) **removes** the interface's private key. See permissions gotcha below. |
| `peer <base64-public-key>` | begin a peer block, identified by its public key | multiple `peer ...` groups may appear in one `set` call |
| `remove` (within a `peer` block) | delete this peer instead of configuring it | must follow a `peer <key>` |
| `preshared-key <file-path>` (within a `peer` block) | path to a file containing the peer's base64 PSK | same file-not-argument rule as `private-key`; `/dev/null`/empty file removes the PSK from that peer; entirely optional |
| `endpoint <ip>:<port>` (within a `peer` block) | initial/override endpoint for this peer | gets **auto-updated** by the kernel/userspace implementation to the most recent source IP:port of a correctly authenticated packet — so a manually-set endpoint can be silently superseded once the peer roams (e.g. across NAT/mobile networks) |
| `persistent-keepalive <interval-seconds>` (within a `peer` block) | seconds between keepalive packets, 1–65535 | optional, off by default; `0` or `"off"` disables; useful when this side is behind NAT/a stateful firewall and rarely initiates traffic itself (man page's example: 25 seconds) |
| `allowed-ips [+\|-]<ip>/<cidr>[,...]` (within a `peer` block) | which source IPs are accepted from this peer, and which destination IPs get routed to it | **default behavior is full replace**, not merge — setting `allowed-ips` with no `+`/`-` prefix replaces the peer's entire AllowedIPs list. Prefix an individual IP with `+` (or leave unprefixed within an otherwise-prefixed list) to add incrementally, `-` to remove incrementally, without touching the rest. An empty string removes all AllowedIPs from that peer. |

**Concerning fact — permissions implications of `private-key`**: because the key must live in a
file (not a CLI argument), that file exists on disk (even if only for the instant `wg` reads it,
in the case of `/dev/fd`-based process substitution) and whoever can read it can extract the
interface's private key entirely. If you write it to a real file rather than a process
substitution or `/dev/stdin`, treat it exactly like any other private key file — `umask 077`/
`chmod 600`, and delete it (or keep it exactly as protected as `wg-private.key` from
`key-generation.md`) once `wg set` has consumed it, since `wg` does not delete the file itself.

### setconf

```
wg setconf <interface> <configuration-filename>
```

| Argument | Meaning | Notes/gotchas |
|---|---|---|
| `<interface>` | interface to configure | required |
| `<configuration-filename>` | path to an INI file, format below | required; **replaces** the interface's entire configuration with the file's contents |

`setconf` is a full, blunt overwrite: any peer or setting present on the interface but absent from
the file is dropped. This is efficient (single netlink transaction) but **disruptive** — active
peer sessions not represented in the new file are torn down. For an in-place update that preserves
untouched peers/sessions, use `syncconf` instead.

### addconf

```
wg addconf <interface> <configuration-filename>
```

| Argument | Meaning | Notes/gotchas |
|---|---|---|
| `<interface>` | interface to configure | required |
| `<configuration-filename>` | path to an INI file, format below | required; **appends/merges** rather than replacing |

Adds the file's peers/settings on top of the interface's existing configuration, rather than
wiping it first. Useful for layering in an additional peer or two from a separate file without
reconstructing the whole configuration.

### syncconf

```
wg syncconf <interface> <configuration-filename>
```

| Argument | Meaning | Notes/gotchas |
|---|---|---|
| `<interface>` | interface to configure | required |
| `<configuration-filename>` | path to an INI file, format below | required |

Like `setconf`, but first reads back the interface's *current* live configuration and diffs it
against the file, applying only the explicit differences. **Much less efficient** than `setconf`
(extra read + diff work) but does **not disrupt existing peer sessions** that are unaffected by the
diff — this is the sub-command to reach for when you've hand-edited a `.conf` file and want the
running interface to catch up without a connectivity blip for peers whose config didn't change.
The canonical pattern: edit the same file `wg-quick` would have brought the interface up from, then
`wg syncconf <if> <(wg-quick strip <if>)` (stripping `wg-quick`-only directives it wouldn't
understand) — or, if the file is already plain `wg`-format INI, pass it directly.

## Configuration file format

Shared by `setconf`, `addconf`, `syncconf` (as input) and `showconf` (as output). INI-based, two
section types:

**`[Interface]`** — exactly one per file:

| Field | Meaning | Required? |
|---|---|---|
| `PrivateKey` | base64 private key, from `wg genkey` | Required |
| `ListenPort` | 16-bit UDP listen port | Optional; random if unset |
| `FwMark` | 32-bit outgoing fwmark; `0`/`"off"` disables; hex allowed with `0x` prefix | Optional |

**`[Peer]`** — zero or more per file:

| Field | Meaning | Required? |
|---|---|---|
| `PublicKey` | base64 public key, from `wg pubkey`; normally received out-of-band from whoever controls that peer | Required |
| `PresharedKey` | base64 PSK, from `wg genpsk` | Optional |
| `AllowedIPs` | comma-separated list of IP/CIDR entries; `0.0.0.0/0` = all IPv4, `::/0` = all IPv6; may repeat | not marked required in the man page, but a peer with none is unreachable/unused in practice |
| `Endpoint` | `host:port` (hostname or IP); auto-updated on receipt of authenticated traffic | Optional |
| `PersistentKeepalive` | seconds, 1–65535, or `0`/`"off"` | Optional, off by default |

Comments start with `#` and run to end of line. Example from the man page (public data, safe to
reuse as a template — do not reuse the literal keys shown, they are illustrative only):

```ini
[Interface]
PrivateKey = yAnz5TF+lXXJte14tji3zlMNq+hd2rYUIgJBgB3fBmk=
ListenPort = 51820

[Peer]
PublicKey = xTIBA5rboUvnH4htodjb6e697QjLERt1NAB4mZqp8Dg=
Endpoint = 192.95.5.67:1234
AllowedIPs = 10.192.122.3/32, 10.192.124.1/24
```

## The "-" gotcha: wg does not treat a dash as stdin

Many Unix CLI tools accept `-` as a filename argument meaning "read stdin" / "write stdout."
**`wg` does not do this for its file-path arguments (`setconf`/`addconf`'s configuration filename,
or `set`'s `private-key <file-path>`/`preshared-key <file-path>`).** Verified directly on this
machine (wireguard-tools 1.0.20260223-1):

```
$ echo "" | wg setconf wg0test -
fopen: No such file or directory
```

`wg` calls `fopen("-")` literally and fails, because no file named `-` exists in the working
directory — it never special-cased the string. The same command with `/dev/stdin` instead gets
past the file-open stage cleanly (it then fails later on a netlink permission check when not run as
root, confirming the parse succeeded):

```
$ echo "" | wg setconf wg0test /dev/stdin
Unable to modify interface: Operation not permitted
```

**Correct pattern**: use `/dev/stdin` explicitly, or (bash-only) process substitution
`<(echo ...)` / `<(some-command)`, wherever these sub-commands want a file path but the real source
is a pipe or inline string. This matters most for `set private-key`/`preshared-key`, where using
`/dev/stdin` or `<(...)` instead of a real temp file is exactly what avoids ever writing the key to
disk (see the `genkey` "never touch a temp file" gotcha above). `genkey`/`pubkey`/`genpsk`
themselves don't have this issue at all — they always read/write stdin/stdout directly with no
filename argument, so there's nothing to get wrong.

Also confirmed on this machine: `/dev/null` as `private-key`'s file-path is accepted syntactically
(distinct from the `-`/no-such-file case) — it's the documented mechanism for *removing* a key from
a live interface, per the man page.

## Environment variables

| Variable | Meaning | Default |
|---|---|---|
| `WG_COLOR_MODE` | `always` / `never` / `auto` — controls ANSI color in pretty-printed `show` output | `auto` (color only to a TTY) if unset or set to something invalid |
| `WG_HIDE_KEYS` | `never` shows private/preshared keys in the pretty-printed `show` output; anything else (including unset) hides them as `(hidden)` | keys hidden — see the `show` gotcha above: this only affects the no-filter pretty-print mode, not `dump`/explicit key filters |
| `WG_ENDPOINT_RESOLUTION_RETRIES` | integer, or `infinity` — retry count for non-permanent DNS resolution errors on a peer's `Endpoint`, with increasing delay between attempts | 15 if unset |

## Debugging information

For live-tunnel troubleshooting (not configuration, but documented in the same man page so noted
here for completeness): on Linux, with the kernel module loaded, dynamic debug output can be
enabled and read via `dmesg(1)`:

```
# modprobe wireguard && echo module wireguard +p > /sys/kernel/debug/dynamic_debug/control
```

OpenBSD/FreeBSD use `ifconfig wg0 debug` instead. Userspace (non-kernel-module) implementations
conventionally honor a `LOG_LEVEL=verbose` environment variable. None of this is `wg`-specific
configuration — it toggles verbosity of the underlying implementation, not anything `wg` itself
sets via netlink.

## Use Cases

- Generate a fresh Curve25519 keypair for a new WireGuard interface, piping directly from `wg
  genkey` into `wg pubkey` so the private key never touches a temporary file on disk.
- Generate a pre-shared key with `wg genpsk` and distribute it out-of-band to a peer, adding a
  symmetric-cryptography layer on top of the public-key handshake for defense against a future
  quantum-capable adversary.
- Inspect a running interface's current peers, their most recent handshake times, and their
  transfer counters with `wg show <interface>` (or `wg show <interface> dump` for a script-parsable
  form) to confirm a tunnel is actually passing traffic and staying alive.
- Check which UDP port an interface is currently listening on, or which fwmark it applies to
  outgoing packets, with `wg show <interface> listen-port` / `wg show <interface> fwmark` when
  debugging a firewall or NAT-traversal issue.
- Dump a running interface's full configuration to a file with `wg showconf <interface> >
  backup.conf` before making changes, so there is a known-good state to roll back to.
- Add a new peer to a running interface immediately with `wg set <interface> peer <pubkey>
  allowed-ips <cidr> endpoint <host:port>`, without restarting the interface or dropping existing
  peers' sessions.
- Remove a peer from a running interface on the fly with `wg set <interface> peer <pubkey> remove`,
  for example when revoking a device's VPN access.
- Rotate an interface's private key in place with `wg set <interface> private-key <path>`, using a
  process-substitution or `/dev/stdin` source so the new key is never written to a persistent file.
- Incrementally widen or narrow a specific peer's allowed traffic ranges with `wg set <interface>
  peer <pubkey> allowed-ips +<cidr>` or `-<cidr>`, without having to restate that peer's entire
  AllowedIPs list.
- Push a hand-edited configuration file onto a live interface with `wg syncconf <interface>
  <file>` when the goal is to apply changes without disrupting peers whose settings didn't change —
  as opposed to `wg setconf`, which would tear down and rebuild every peer session unconditionally.
- Layer additional peers from a separate file onto an already-configured interface with `wg
  addconf <interface> <file>`, without needing to merge that file's contents into the main
  configuration by hand first.
- Fully replace a running interface's configuration in one shot with `wg setconf <interface>
  <file>` when a clean, from-scratch reconfiguration (accepting the session-disruption cost) is
  actually what's wanted.
- List every WireGuard interface currently present on the system with `wg show interfaces`, as a
  first step in any script that needs to iterate over all tunnels.
- Disable a persistent keepalive that's no longer needed (e.g. after a peer stopped being behind
  restrictive NAT) with `wg set <interface> peer <pubkey> persistent-keepalive 0`, reducing
  unnecessary keepalive traffic.
